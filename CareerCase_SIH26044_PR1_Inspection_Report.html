1. Task Understanding

What PR1 must deliver (plain language)

There are two main surfaces, both entirely on the industry/recruiter side:

Surface A — Opportunity Authoring

An employer-facing multi-section draft form that lets a recruiter (Riya-persona) build and publish a structured job/internship opportunity. Every requirement must:

  • Preserve the exact literal wording typed by the author
  • Track whether a skill was canonically resolved, needs human review, or is unresolved
  • Carry a HumanConfirmationTrace before the opportunity version may be called "confirmed"
  • Support an optional AI-assisted extraction preview — with source text shown, confidence disclosed, and accept/edit/reject actions required — but AI never auto-publishes
  • Produce a versioned OpportunityVersion (type, audiences, requirements, eligibilityRules, source) that Laya's student explorer can consume by opportunityId

Surface B — Recruiter Applicant Workspace

An industry-facing list of applications for opportunities the recruiter's organization owns. From that list:

  • Open an applicant detail view backed exclusively by the RecruiterApplicationProjection / ProductionRecruiterProjection allowlist
  • Display readiness band as decision support (not as a hiring probability or ranking)
  • Record explicit human stage actions (under_review → shortlisted → offered / rejected_by_human) with notes, using SihBrowserDal.transitionApplicationStage()
  • Block detail access immediately when consent is withdrawn — never cache a full applicant object past the consent check

Key architectural facts discovered

  • No sih/industry/ or sih/recruiter/ directory exists yet — both must be created fresh. This is clean; there is no collision risk.
  • Routes.ts has no /industry/ or /recruiter/ routes — these will need to be added. This is a protected file (see §4) — the minimal registration needs Kamal's review. See §9 for the resolution path.
  • The demo runtime already has a working recruiter page at /demo/recruiter using RecruiterApplicationProjection — Harsh's real pages replicate the same field boundaries.
  • buildProductionRecruiterProjection() has a built-in validateNoProhibitedKeys() that throws at runtime if any prohibited key is passed — this is the enforcement layer.
  • SihBrowserDal.transitionApplicationStage() is the only browser-callable method for recording human application stage events — it writes to application_events via RLS.
  • No opportunity authoring DAL method exists in SihBrowserDal — opportunity insert/update appears to be a trusted Worker operation or the recruiter writes to a browser-RLS-permitted table. This must be confirmed before building the authoring form (see §9, Risk R1).
